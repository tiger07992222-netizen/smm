# Отчёт: архитектура SMM-пайплайна Scores24

Документ собирает договорённости из обсуждения и сверяет их с текущим кодом в `tg_smm`.  
Цель — один источник правды: **что система делает, из чего состоит, как течёт состояние, зачем каждый шаг**.

---

## 1. Зачем это существует

SMM сейчас вручную собирает три поста в день в Telegram-канал Scores24:

| Рубрика | Слот (МСК) | Суть |
|---|---|---|
| Экспресс | 11:00 | Несколько ног, общий кэф |
| Ставка дня | 14:00 | Одна нога |
| Тренд | 17:00 | Одна нога + вывод |

После матча пост дописывают `✅✅✅` или `❌❌❌`.

Агент должен:

1. Сам забрать прогнозы (API утром / JSON).
2. Выбрать пики под коридоры кэфов.
3. Собрать пост: факты из данных + короткая обёртка (LLM только intro).
4. Проверить факты; при ошибке починить (кэфы + текст) до 3 раз.
5. Утверждённые посты увести в канал по слотам **без превью**.
6. В админ-бот слать **только** то, что валидатор не смог починить.
7. После результата матча отредактировать пост.

Нейронка **не** ходит в API с ключом, **не** выбирает матчи, **не** считает кэф, **не** публикует и **не** ставит галочки. Это делает код.

## 2. Пайплайн (as-is)

### 2.1. Ops-граф

```
bootstrap(channel)
  → fetch_data(from channel.data_source)
  → select_rubrics(from channel.rubrics)
  → generate(facts + PromptTemplate)
  → validate(facts↔text) ⇄ repair(errors)
  → adapt(platform) → publish → settle
```

- `Channel` = platform + locale + content_profile + rubrics + data_source + prompt_ids + binding.
- Страны/каналы одного профиля — только yaml; новый `content_profile` — другой набор узлов.
- State = TypedDict; узлы возвращают **patch**.
- Промпты в bootstrap по `prompt_ids` + `{locale}` через PromptTemplate.
- Превью как обязательный узел — **нет**.

## 3. Из чего состоит система

### 3.1. Слои

| Слой | Роль | Где |
|---|---|---|
| Config / destination | Кто публикуем, когда, на каком языке | `config/channels/*.yaml`, дальше — БД destinations |
| Bootstrap | Собирает AgentState + промпты перед графом | сейчас частично runtime; to-be `bootstrap.py` |
| Ops graph | Оркестрация intents | `smm/agent/graph.py` |
| Tools / services | Реальная работа (HTTP, SQLite, TG) | `smm/tools/ops.py`, `scores24_api`, `pipeline`, `publisher`, `settler` |
| Skills | Текстовые правила для LLM | `smm/skills/*.md` |
| Durable store | Пики, кэш API, черновики, привязки | `data/` + SQLite |
| Admin bot | Люди чинят только failed | `smm/bot.py` |
| Scheduler | Утро fetch+generate; тик publish; settle | `smm/main.py` |

### 3.2. Главные сущности данных

**Pick** — готовый прогноз на день (экспресс / ставка / тренд) с ногами, кэфами, `stat_text`.

**Leg** — одна нога: матч, линия, кэф, статистика.

**Draft** — черновик поста канала: текст, HTML, картинка, `locked_facts`, статус, слот, `message_id`, settlement.

**MatchResult** — счёт/статус матча для сеттла.

**LLM view** — обезличенный снимок API (`predictions_top_llm.json`): матчи, линии, кэфы. Без секрета `X-Internal-Request`.

### 3.3. Статусы Draft (жизненный цикл поста)

```
generated → approved → published → settled
                ↘ needs_human  (ручная правка → снова approved / publish now)
                ↘ skipped
                ↘ failed
```

| Статус | Зачем |
|---|---|
| `generated` | Только что собран, ещё не прошёл валидатор |
| `approved` | Можно слать по слоту; в личку **не** шлём |
| `needs_human` | 3 ремонта не хватило / нечиняемая ошибка → алерт + карточка в боте |
| `published` | Уже в канале, ждём результат |
| `settled` | Дописали ✅/❌ |
| `skipped` | SMM нажал «не публиковать» |
| `failed` | Ошибка Telegram на слоте |

## 4. Узлы пайплайна — нормальное объяснение

Короткая таблица «Узел → одна фраза» — это только оглавление. Ниже по каждому узлу: **какую проблему закрывает**, **что происходит по шагам**, **что на входе/выходе**, **как меняется state**, **кто исполняет** (код / LLM / человек), **что если сломалось**.

Общая идея цепочки: сначала достаём правду о матчах → выбираем купоны → собираем пост → проверяем → чиним → подгоняем под Telegram → публикуем → закрываем результат. Человек появляется только в `escalate`.

---

### 4.1. `bootstrap` — сборка контекста запуска

**Проблема.** Если промпты, язык и id канала зашиты внутри узлов, каждый новый канал (EN-теннис, Facebook) требует правок Python. Граф начинает «знать слишком много».

**Что делает.** Это слой *до* графа (оркестратор / `bootstrap.py`). Он читает destination из yaml/БД и собирает начальный `AgentState`:

- куда публикуем: `destination_slug`, `platform` (telegram/…), `telegram_chat_id`;
- на каком языке и в какой таймзоне: `locale`, `timezone`, `day`;
- какой прогон: `intent` (`generate` / `tick` / `publish` / `settle`);
- какие промпты уже готовы: `prompts[]` — `PromptBundle` для copywriter / validator / repair (и позже adapter), без хардкода строк в узлах.

Потом только `graph.invoke(state)`.

**Вход:** slug канала + intent + настройки.  
**Выход:** полный стартовый state.  
**Кто:** только код. LLM здесь нет.

**Зачем отдельно.** Узлы дальше тупые и переиспользуемые: им дали locale=`en` и английский PromptBundle — они пишут по-английски из фактов, а не «переводят русский пост».

*Сейчас:* частично runtime + `config/channels/*.yaml`. Отдельного bootstrap-файла ещё нет.

---

### 4.2. `ingest` — доставка фактов

**Проблема.** Без свежих пиков copywriter и LLM начнут выдумывать или работать на вчерашних данных. Секрет API нельзя отдавать модели.

**Что делает программа:**

1. Подхватывает JSON из `data/incoming` (ручная/бэкенд-доставка), если есть.
2. На утреннем `generate` (и CLI `fetch`) делает  
   `GET /rapi/predictions/top` с заголовком `X-Internal-Request` из `.env`.
3. Парсит ответ (`block_type` → express / bet / trend) в список `Pick` с ногами и кэфами.
4. Пишет на диск: raw-кэш API, `picks/<channel>/<day>.json`, и **sanitized** `predictions_top_llm.json` для LLM.

Минутный `tick` этот GET **не** вызывает — только утро / явная генерация.

**Вход:** intent, credentials в env, опционально файлы.  
**Выход (durable):** пики и LLM-view.  
**Patch в state:** notes вроде `api picks=12`.  
**Кто:** код. LLM может потом только *прочитать* кэш (`view_api_predictions`), без сети и без ключа.

**Если API упал (403/таймаут):** ошибка в notes; день может пойти со старыми файлами/incoming или уйти в алерт «нет пиков».

---

### 4.3. `select` — выбор купонов дня

**Проблема.** В API приходит пачка прогнозов. В канал нужны ровно три рубрики, с адекватным кэфом (не «экспресс на 15.0»), и с возможностью «взять другой пик», если SMM отбраковал текущий.

**Что делает.** Для `express`, `bet`, `trend` независимо:

- фильтрует по типу и `skip_ids` (уже отвергнутые);
- считает попадание в **коридор кэфов** из конфига;
- предпочитает более «сильные» серии (hits/sample и т.п.);
- кладёт ровно один выбранный `Pick` на рубрику.

**Вход:** пики дня + corridors + skip_ids.  
**Выход:** `selected.express|bet|trend` (или сразу три draft-потока).  
**Кто:** только код. LLM не выбирает матчи.

**Зачем до generate.** Текст и картинка строятся уже от зафиксированного купона. Иначе модель «выбирает» исход и начинает фантазировать линии.

*Сейчас:* логика внутри `generate_day` / `selector.py`, не отдельный узел графа.

---

### 4.4. `generate` — сборка черновика поста

**Проблема.** Нужен пост в стиле канала, но цифры (кэф 1.76, «10 из 11») должны быть дословны из данных. Если отдать LLM весь пост — она регулярно врёт цифрами.

**Что делает код (каркас):**

- спорт, флаги стран, `Команда — Команда`, линия, кэф, блок 📊 из `stat_text`;
- три ссылки/CTA из каталога (не из головы модели);
- PNG-карточка (Pillow);
- список `locked_facts` — «что считается истиной» для валидатора;
- слот публикации (`slot_at` 11:00 / 14:00 / 17:00).

**Что делает LLM (узко):** только короткая обёртка — `intro` (и у тренда `closing`) по skill + facts.  
Нет ключа / модель вставила чужое число → intro отбрасывается, берётся шаблон.

**Вход:** выбранный Pick + PromptBundle copywriter + links.  
**Выход:** `Draft` со статусом `generated`, текст/html/caption/image/`locked_facts`.  
**Кто:** код + опционально LLM на intro.

**Зачем так режем зоны ответственности.** Модель отвечает за тон («уже готов 😎»), код — за купон. Это главное архитектурное правило продукта.

---

### 4.5. `validate` — пропуск в эфир или в ремонт

**Проблема.** Даже с каркасом intro может добавить «12 из 13», сломать длину caption, упомянуть матч который уже начался, или написать «гарантированно зайдёт».

**Что делает.**

1. **Железные проверки (код, всегда):**  
   все `locked_facts` присутствуют в тексте; нет лишних чисел вне фактов/даты/разрешённого промо; длина с запасом под `✅✅✅`; картинка на месте; ссылки с `http(s)`/`t.me`; kickoff ещё в будущем относительно слота; стоп-слова.
2. **LLM-validator (если есть ключ):** те же смыслы + тон, но решение всё равно сводится к списку `errors[]`.

**Вход:** Draft + now + already_published.  
**Выход:** `errors[]` (пусто = ок).  
**Ветвление:**

- ошибок нет → `adapt` (дальше approved);
- ошибки чинимые и `attempt < 3` → `repair`;
- нечиняемые или попытки кончились → `escalate`.

**Кто:** код всегда; LLM опционально как второй взгляд.

**Зачем не публиковать сразу после generate.** Один плохой пост в канале дороже трёх автоматических циклов починки.

---

### 4.6. `repair` (до 3 раз) — починка фактов и текста

**Проблема.** Валидатор нашёл расхождение. Просто «перепиши intro» недостаточно: кэф в тексте мог устареть относительно API, а модель не должна сама придумывать новый коэффициент.

**Порядок внутри одной попытки (жёсткий):**

1. **Программа** синхронизирует кэфы с актуальным store / кэшем `/predictions/top` (`sync_pick_odds`).
2. **Программа** пересобирает body и `locked_facts` (и карточку, если кэф изменился).
3. **LLM** чинит narrative под *уже обновлённые* facts и список ошибок из валидатора.
4. `validation_attempt += 1` → снова `validate`.

**Вход:** Draft + errors + attempt.  
**Выход:** обновлённый Draft (и возможно новый pick.odds).  
**Кто:** сначала код (odds), потом LLM (слова).

**Нечиняемое сразу в escalate (без трёх кругов):** матч уже идёт, нет картинки, битая ссылка, пост уже published.

**Зачем ×3.** Баланс: дать автомату шанс, но не крутить бесконечно и не спамить API/LLM.

---

### 4.7. `adapt` — формат платформы

**Проблема.** Смысл поста один, а ограничения разные: у Telegram caption ≤1024, HTML-ссылки, нужен запас под три символа сеттла; у другой соцсети — другие лимиты и разметка.

**Что делает.** Берёт уже *валидный по фактам* draft и приводит к wire-формату destination:

- Telegram: `text_html`, обрезка caption, `edit_as` (caption vs text), флаги API (`disable_web_page_preview`);
- позже Facebook/др. — свой адаптер.

Смысл и цифры тут **не** переписываются — только упаковка.

**Вход:** approved-по-фактам draft + `platform` из state.  
**Выход:** draft, готовый к `sendPhoto`/`sendMessage`; статус обычно `approved`.  
**Кто:** код (адаптер платформы).

**Зачем отдельным узлом.** Новый канал Telegram = конфиг. Новая платформа = новый адаптер, без копипасты generate/validate.

*Сейчас:* частично размазано по `render_post` / `publisher`.

---

### 4.8. `publish` — выход в канал по слоту

**Проблема.** Нельзя требовать от SMM каждое утро жать «ок» на три нормальных поста. Ручная приёмка нужна только на сбоях.

**Что делает.** Ищет draft’ы `approved` с `slot_at <= now` (и привязанным chat id), отправляет в канал, сохраняет `message_id` / `published_at`, ставит `published`.

**Чего не делает:** не шлёт превью всех approved в личку. Тихий автопилот.

**Вход:** очередь approved + время.  
**Выход:** сообщение в канале + durable статус.  
**Кто:** код (Telegram Bot API).  
**Если TG недоступен:** `failed` + алерт в админ-бот.

---

### 4.9. `settle` — закрытие результата

**Проблема.** После матча SMM вручную дописывает галочки. Это рутина и источник ошибок (забыли, перепутали экспресс).

**Что делает.** Для `published` + `settlement=pending`:

1. Ждёт kickoff + типичную длительность спорта (не общий «раз в сутки»).
2. Читает `MatchResult` по `match_id` ног.
3. Считает ногу won/lost/void; для экспресса — агрегирует (одна lost → весь lost; все void → void).
4. Редактирует сообщение в канале: дописывает `✅✅✅` или `❌❌❌`.
5. Ставит `settled`. При void — алерт без галочек.

**Вход:** published drafts + match results.  
**Выход:** отредактированный пост в TG + settlement.  
**Кто:** код. LLM не участвует.

---

### 4.10. `escalate` — человек как исключение

**Проблема.** Автомат исчерпал попытки или упёрся в нечиняемое. Молчать нельзя — пост либо не выйдет, либо выйдет кривым.

**Что делает.**

1. Ставит draft `needs_human`.
2. Пишет в админ-бот **список ошибок валидатора**.
3. Присылает **только этот** черновик с кнопками: другой текст / другой пик / правка / своё фото / в канал сейчас / не публиковать.

**Чего не делает:** не превьюит все три успешных поста дня.

**Вход:** Draft после проваленного validate/repair.  
**Выход:** сообщение оператору; дальнейший путь — руки SMM → снова approved/publish или skip.  
**Кто:** код + человек.

**Зачем так.** Операторы не должны разгребать «всё ок» три раза в день. Их время — на исключения.

---

### Как узлы связаны одной фразой

```text
bootstrap  готовит «кто/куда/на каком языке/какими промптами»
ingest     приносит правду о прогнозах (код + секрет)
select     выбирает три купона дня
generate   собирает пост: факты кодом, intro моделью
validate   решает: в эфир, в ремонт или к человеку
repair     обновляет кэфы из API, потом чинит слова
adapt      упаковывает под Telegram (или другую платформу)
publish    сам постит по слоту
settle     сам дописывает ✅/❌
escalate   зовёт SMM только когда автомат сдался
```

## 5. Состояние графа: что хранит и как меняется

### 5.1. Два «состояния» — не путать

| Вид | Где живёт | Зачем |
|---|---|---|
| **AgentState** (прогон графа) | В памяти на один `invoke` | Оркестрация: intent, счётчики, notes, (to-be) draft/errors/prompts |
| **Durable state** | SQLite + JSON на диске | Правда о дне: пики, черновики, message_id, settlement |

Граф **не** является БД. После прогона важные вещи обязаны оказаться в store.

### 5.2. Текущий AgentState (as-is)

```text
intent, channel_slug, day, post_type, force, skip_ids,
created, published, needs_human, notes[]
```

Обновление: узел возвращает patch через `{**state, **kwargs}` (новые notes дописываются).  
Черновик и ошибки валидации сейчас живут **внутри** `Draft` в SQLite, а не в полях графа.

### 5.3. Целевой AgentState (to-be, Pydantic)

```text
intent
destination_slug, platform, locale, timezone, day
prompts: [PromptBundle(role, template, variables)]

# рабочее тело одного (или пачки) постов
picks / selected
draft
errors[]
validation_attempt
status          # approved | needs_human | ...
published_count, notes[]
```

Правило: **узел возвращает только изменённые поля**, не `state["x"] = ...`.

### 5.4. Как state меняется по графу (целевой день)

Ниже — один утренний прогон `intent=generate` для destination `scores24` (ru / telegram).

#### Старт (после bootstrap)

```json
{
  "intent": "generate",
  "destination_slug": "scores24",
  "platform": "telegram",
  "locale": "ru",
  "timezone": "Europe/Moscow",
  "day": "2026-08-26",
  "prompts": [
    {"role": "copywriter", "template": "..."},
    {"role": "validator", "template": "..."},
    {"role": "repair", "template": "..."}
  ],
  "validation_attempt": 0,
  "errors": [],
  "draft": null,
  "notes": []
}
```

#### После `ingest`

- На диск: raw API + `predictions_top_llm.json` + `picks/scores24/2026-08-26.json`.
- В state (patch): `notes += ["api picks=N"]`, возможно ссылка на кэш.
- Промпты / locale **не меняются**.

#### После `select`

```json
{
  "selected": {
    "express": { "id": "express-...", "total_odds": 3.24, "legs": ["..."] },
    "bet": { "..." },
    "trend": { "..." }
  }
}
```

#### После `generate` (на один post_type; цикл ×3 рубрики)

```json
{
  "draft": {
    "post_type": "express",
    "text": "...",
    "text_html": "...",
    "locked_facts": ["3.24", "ПСВ", "1.76", "..."],
    "image_path": "...",
    "slot_at": "2026-08-26T11:00:00+03:00",
    "status": "generated"
  },
  "validation_attempt": 0,
  "errors": []
}
```

#### После `validate` (если плохо)

```json
{
  "errors": ["лишние числа: 12, 13", "..."],
  "draft.status": "generated"
}
```

Ребро: есть ошибки и `attempt < 3` и чинимо → `repair`, иначе → `escalate` или `adapt`.

#### После `repair`

```json
{
  "validation_attempt": 1,
  "draft.pick": { "...odds обновлены из API..." },
  "draft.locked_facts": ["...новые..."],
  "draft.text": "...пересобранный...",
  "errors": []
}
```

Снова `validate`. До 3 попыток.

#### Успех → `adapt` → persist approved

```json
{
  "draft.status": "approved",
  "draft.caption": "≤1024 html...",
  "errors": []
}
```

Пишется в SQLite. В личку **ничего**. State прогона может закончиться (`generate` → END).

#### Провал → `escalate`

```json
{
  "draft.status": "needs_human",
  "needs_human": 1,
  "errors": ["..."]
}
```

Алерт + превью **только этого** черновика.

#### Дневной `tick` / `publish`

Отдельный invoke:

```json
{ "intent": "tick" или "publish", "published": 1, "notes": ["published=1"] }
```

Durable: Draft `approved` → `published`, заполнены `message_id`, `published_at`.

#### Вечерний `settle`

```json
{ "intent": "settle", "notes": ["settle ran"] }
```

Durable: `settlement=won|lost|void`, статус `settled`, текст в TG дополнен.

## 6. Intents: какие прогоны бывают

| Intent | Цепочка | Когда |
|---|---|---|
| `generate` | ingest(+API) → generate(+validate/repair) | Утро `generate_at`, `/generate`, CLI |
| `tick` | ingest(файлы) → generate(досбор) → publish | Каждую минуту (упрощённо сейчас) |
| `publish` | publish | Явно / отладка |
| `settle` | ingest → settle | Раз в N минут |

**Зачем разные intents:** один граф, разные входы — не плодить пять ботов.

**Улучшение расписания (договорились по смыслу):** лучше не «полный tick каждую минуту», а:

- утро: fetch + generate;
- слоты 11/14/17: только publish этой рубрики;
- settle: редкий poll.

## 8. Multi-destination (зачем так проектировали)

Чтобы добавить канал «теннис EN» или Facebook SV **без** форка пайплайна:

platform: telegram
locale: en
timezone: Europe/London

## 12. Принципы (коротко «зачем так»)

1. **Факты священны** — цифры из API/store; LLM их не выдумывает.
2. **Секреты у программы** — LLM видит только sanitized результат.
3. **Патчи state** — прозрачный граф, проще replay и несколько destinations.
4. **Конфиг > код** — новый канал той же платформы без деплоя логики.
5. **Человек — исключение** — в бот только то, что автомат не починил.
6. **Один граф — много intents** — утро / слот / сеттл не размножают архитектуру.
